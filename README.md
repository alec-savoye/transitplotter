# TransitPlotter

Live NYC subway map. A backend polls the MTA's realtime feeds, computes where
every train is *right now* (the feeds don't give coordinates — see below), and
streams positions over WebSocket to a browser that renders them moving between
stations on a stylized subway map.

- **Backend** (`server/`): Node.js/TypeScript. Polls feeds, computes positions,
  broadcasts over WebSocket, serves static map geometry over HTTP.
- **Frontend** (`web/`): Vite + MapLibre GL. A "dumb" renderer — it just draws
  the positions the backend sends and tweens between them.
- **Shared** (`shared/`): the tiny wire contract shared by both.

Everything runs in Docker; nothing is installed on the host.

---

## Data sources

All MTA feeds below are **free and require no API key or account** (MTA removed
that requirement in 2024). See the MTA developer portal:
<https://api.mta.info/> and <https://www.mta.info/developers>.

### 1. Realtime feeds — *where the trains are* (polled every 20s)

Defined in [`server/src/feeds.ts`](server/src/feeds.ts).

Base URL: `https://api-endpoint.mta.info/Dataservice/mtagtfsfeeds`

There are **eight feeds, one per line group**. (`%2F` is a URL-encoded `/`.)

| Key        | URL suffix          | Lines covered              |
| ---------- | ------------------- | -------------------------- |
| `numbered` | `/nyct%2Fgtfs`      | 1 2 3 4 5 6 7 S + shuttles |
| `ace`      | `/nyct%2Fgtfs-ace`  | A C E                      |
| `bdfm`     | `/nyct%2Fgtfs-bdfm` | B D F M                    |
| `g`        | `/nyct%2Fgtfs-g`    | G                          |
| `jz`       | `/nyct%2Fgtfs-jz`   | J Z                        |
| `l`        | `/nyct%2Fgtfs-l`    | L                          |
| `nqrw`     | `/nyct%2Fgtfs-nqrw` | N Q R W                    |
| `si`       | `/nyct%2Fgtfs-si`   | Staten Island Railway      |

Full example URL:

```
https://api-endpoint.mta.info/Dataservice/mtagtfsfeeds/nyct%2Fgtfs-l
```

**Format:** each feed returns a **GTFS-realtime protobuf** payload (binary,
`application/x-protobuf` — *not* JSON), regenerated by MTA about every 30s. We
decode it with the [`gtfs-realtime-bindings`](https://www.npmjs.com/package/gtfs-realtime-bindings)
package in [`server/src/parse.ts`](server/src/parse.ts).

**Important quirk:** the NYC subway feed's `VehiclePosition.position` field is
**not populated** — there are no train coordinates. Per active trip you only
get its upcoming stops with *predicted arrival/departure times*. So the backend
**synthesizes** each train's coordinate by interpolating along the real track
geometry between its previous and next stop based on those predicted times.
(Reference: MTA GTFS-realtime docs, <https://www.mta.info/document/134521>.)

### 2. Static feed — *the map itself* (downloaded once, cached)

Defined in [`scripts/build-static.ts`](scripts/build-static.ts).

```
https://rrgtfsfeeds.s3.amazonaws.com/gtfs_supplemented.zip
```

A ZIP of GTFS CSV files (`stops.txt`, `routes.txt`, `trips.txt`, `shapes.txt`,
`stop_times.txt`). This provides station coordinates, route colors, and the
track polylines the trains are interpolated along. It's downloaded once and
cached as SQLite (see caching below). MTA updates it every few weeks.

The URL can be overridden with the `GTFS_STATIC_URL` env var.

## Caching (off the boot drive)

Large cached assets must **not** live on the boot drive. The static GTFS SQLite
DB is stored under:

```
/srv/active-raid/LIBRARIES/247/tmp-trainsplotter/gtfs_static.sqlite
```

This directory is bind-mounted into the containers at `/cache` (see
`docker-compose.yml`, `GTFS_CACHE_HOST` / `GTFS_CACHE_DIR`). The DB is **not**
committed to the repo. Override the host path with `GTFS_CACHE_HOST`.

## Running (Docker only)

```bash
# 1. Build images
docker compose build

# 2. Download + cache the static GTFS DB (one-time; behind the "tools" profile)
docker compose run --rm build-static          # add -e FORCE=1 to rebuild

# 3. Run the app
docker compose up server web
```

- **Map UI:**  http://localhost:5173  (or `http://<LAN-IP>:5173`)
- **Backend API:** http://localhost:8090  (host 8080 is used by pihole, so the
  host port is 8090 mapped to the container's 8080)

For LAN testing, the web app derives the backend host from the browser's
location automatically, so `http://<LAN-IP>:5173` just works.

### Backend HTTP endpoints

| Path             | Description                                  |
| ---------------- | -------------------------------------------- |
| `/health`        | liveness check                               |
| `/routes`        | route metadata (id, color, name) as JSON     |
| `/geo/routes`    | route line geometry as GeoJSON               |
| `/geo/stations`  | station points as GeoJSON                    |
| WebSocket `/`    | pushes `{ t, trains: [...] }` once per second |

## How positions are computed

1. **Boot:** load the static SQLite into memory and build a canonical
   "line" per route + direction (a representative shape polyline with every
   stop projected onto it to get its distance along the track).
2. **Poll (20s):** fetch all 8 realtime feeds, decode protobuf, extract each
   trip's upcoming stop predictions.
3. **Build legs:** for each train, find the segment it's on (previous stop ->
   next stop) and look up both stops' distances along the canonical line.
4. **Tick (1s):** `progress = (now - departTs) / (arriveTs - departTs)`, then
   find the point at that fraction along the shape. Stalled trains (feed
   timestamp >90s stale) are frozen. Broadcast all positions over WebSocket.
5. **Browser:** tweens each train between the 1s snapshots with
   `requestAnimationFrame` for smooth motion.
